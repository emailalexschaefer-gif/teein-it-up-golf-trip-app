## 1. EXISTING ARCHITECTURE DISCOVERED (per the brief's own "audit
first" instruction)

Read directly from `slideshowDeck.ts` before changing anything:
slides are generated by `buildSlideshowDeck`/`rebuildDeckFromOrder`,
both of which call a shared private `buildCoreSlides`. Memories are
filtered by a flat `source` ('favourites'/'all'/'selected'), sorted
chronologically (`sortMemoriesChronologically` -- created_at, then
momentId as a deterministic tie-break), then walked once: opening,
event-level photos, then per round in ordinal order (divider, that
round's photos, Side Game winner slides, Makers & Breakers), then
Champion/Leaderboard, then Bloopers, then closing. This confirmed the
brief's own framing exactly: the existing builder has no concept of
"scope" or "section" at all -- it always walks every round and every
available result type, with the only real control being which
Memories are in the photo stream. Section 2 below is the direct
architectural response to that gap.

## 2. ROOT CAUSE -- SIDE GAME DUPLICATION

Confirmed directly in `buildCoreSlides`'s prior code: the round's
regular photo loop (`for (const m of roundMemories) ...`) drew from
every selected Memory in that round, including ones with
`sourceType === 'SIDE_GAME'` -- with no coordination against the
separate winner-slide loop immediately after it, which could resolve
the exact same photo (matched by `sideCompId` + `playerId`) as a
winner's own image. A winning photo could therefore render twice: once
as an ordinary photo slide, once as the dedicated winner slide reusing
the identical image. Fixed by resolving every round's winner-matched
photos FIRST (same stable sideCompId/winnerPlayerId identity the
winner slide itself already used, never a display-string match, per
the brief's own explicit instruction), then excluding those specific
moment ids from the regular photo stream before it's built -- so a
winning photo is now structurally guaranteed to appear exactly once.
Applied to the existing `buildCoreSlides` (so the current gallery flow
is fixed too, not just the new builder) and independently re-applied
inside the new `buildPresentationDeck` (its own per-round section
toggles mean its control flow has genuinely diverged from
`buildCoreSlides`, not just cosmetically, so the fix needed its own
implementation there rather than a shared call).

## 3. ROOT CAUSE -- EMPTY MAKERS & BREAKERS SECTIONS

Audited directly, not assumed: the existing code already only pushes
a `makersBreakers` slide `if (roundHighlights.length > 0)` --
structurally, an empty-content divider-with-nothing-after-it could not
have come from this exact code path as written. The most likely
explanation for what live testing observed is a production-data
mismatch upstream of this check -- `parsePublishedHighlights` silently
returns `[]` for anything that doesn't match the exact `Highlight`
shape it expects (kind/title/playerName/statLine), by design, rather
than throwing -- so if `published_round_highlights.highlights` in a
real round's data was stored in a subtly different shape (or the
divider the testers saw came from a since-changed earlier version of
this code), it would read as "no content" and should have produced no
divider at all under the code as it stands today. Confirmed this is
correctly guarded in the new `buildPresentationDeck` as well (the same
check, applied before any section is added, with a dedicated test
proving a round with every toggle on but zero real content produces no
section at all) -- not re-architected, since the audit found no
structural flaw to fix, only confirmed the existing guard is sound and
carried it into the new builder.

## 4. ROOT CAUSE -- FINAL LEADERBOARD LANDSCAPE/SCROLL BUG

Confirmed directly in `EventHighlightsPlayer.tsx`: the leaderboard's
row container used `maxHeight: '100%'` with `overflowY: 'auto'` --
precisely what produces "only one large row visibly rendered, with an
internal scrollbar" on a real screen, since nothing can scroll during
unattended slideshow playback. Fixed structurally: removed every
overflow/scroll property from this slide's layout entirely. The row
list is now a flex column (`justify-content: space-evenly`) that
distributes its (already-paginated, max 10) rows to genuinely fill the
fixed available space, with `clamp()`-based font sizing so rows shrink
together on a shorter canvas rather than ever overflowing it. The
existing pagination (10 per page, already built, already tested) is
unchanged and is exactly the brief's own recommended "Top 10, multiple
slides rather than scrolling" behaviour -- the bug was in the CSS
rendering those already-correct pages, not in the pagination logic
itself.

## 6. NEW PRESENTATION CONFIGURATION / DATA MODEL

Per the brief's own Part 18, added as explicit, named types (not UI
conditionals), all in `slideshowDeck.ts`:
- `SectionType` -- the 10 section kinds the brief lists (ROUND_RESULTS
  excluded; see item 11).
- `PresentationScope` -- `{ kind: 'round', roundId }` or
  `{ kind: 'fullEvent' }`.
- `RoundSectionConfig` -- per-round toggles: bestMoments,
  sideGameWinners, makersBreakers.
- `PresentationConfig` -- the full configuration: scope, top-level
  toggles (eventOpening, groupPhoto, eventChampion, finalLeaderboard,
  bloopers, eventFinale), an ordered `rounds: RoundSectionConfig[]`
  (the organiser's own round order and selection, not auto-derived),
  and a shared bestMomentsSource (favourites/all/selected) +
  selectedMomentIds, reusing the existing, already-proven
  favourites-first pattern rather than inventing a parallel mechanism.
- `getAvailableSections(data, scope)` -- tells a picker UI which
  toggles to even offer, with a human-facing label and, when
  unavailable, a reason (brief Part 2's "only show sections that can
  actually produce meaningful content").
- `defaultPresentationConfig(data, scope)` -- intelligent defaults,
  described exactly in items 7/8 below.
- `buildPresentationDeck(data, config)` -- the deterministic generator:
  one config always produces the same deck. Reuses
  `sortMemoriesChronologically`, `toPhotoSlide`, `formatDateRange`, and
  `parsePublishedHighlights` directly from the existing module --
  every one of those functions' existing guarantees (deterministic
  tie-breaking, no invented metadata, verbatim Makers & Breakers, never
  throwing on malformed data) carries over unchanged, not
  reimplemented.

The existing `buildSlideshowDeck`/`rebuildDeckFromOrder`/
`photoMomentIdsInOrder` are completely unchanged in their own public
signature and still work exactly as before (aside from both also now
benefiting from the Section 2 duplication fix) -- this is a genuine
addition, not a replacement, matching "do not redesign or rebuild the
slideshow engine."

## 7. DEFAULT BEHAVIOUR -- ROUND PRESENTATION

Round Intro + Best Moments + Side Game Winners + Makers & Breakers,
each individually defaulted ON only where `getAvailableSections`
itself confirms real content exists for it -- the exact same
availability check a picker UI would use, not a second,
separately-maintained rule that could drift from it. A round with
photos but no official winners yet, for example, defaults to Best
Moments on, Side Game Winners off.

## 8. DEFAULT BEHAVIOUR -- FULL EVENT PRESENTATION

Event Opening on; Group Photo on only if one is genuinely selected;
every round gets Best Moments on if it has photos (favourites-only by
default, never "all," per "concise"); **only the chronologically last
round** gets Side Game Winners/Makers & Breakers defaulted on -- every
earlier round defaults to Best Moments alone, directly implementing
"avoid automatically replaying every Makers & Breakers selection and
every Side Game from every previous round... the organiser can
explicitly turn them on." Event Champion/Final Leaderboard default on
only if the event has an authoritative champion (i.e. is complete);
Bloopers on only if at least one genuinely exists; the closing slide
always on by default. Confirmed by a dedicated test with two rounds
and real Side Game winners in both -- the first round's winners/M&B
default off, the second's default on.

## 12. DEFERRED ITEMS, AND WHY

Named directly, not left implicit:

- **The organiser-facing UI itself** -- "Create Slideshow → Choose
  Scope → Choose Sections → Review → Play," the rename from "Produce
  Slideshow," and the actual section-toggle checkboxes described
  throughout the brief. The entire deterministic generation engine
  this UI would drive (`buildPresentationDeck`,
  `defaultPresentationConfig`, `getAvailableSections`) is built and
  tested; the screens that call it are not. Given the scale of this
  brief and the time this session had, building a genuinely good
  multi-step wizard UI without time left to verify it properly felt
  like a worse outcome than delivering a complete, tested foundation
  and being honest that the UI is the next, clearly-scoped piece of
  work -- rather than shipping UI code with no confidence behind it.
- **Round Results / Leaderboard for an individual round** (brief Part
  2's "Round Results / Leaderboard where supported"). Not included in
  `RoundSectionConfig` at all. No per-round result distinct from the
  one authoritative event-level Champion/standings exists anywhere in
  the data model (`computeFinalResults` produces a single event-level
  result only) -- inventing a "round result" from partial cumulative
  standings would be exactly the kind of result this whole feature has
  always refused to fabricate. Flagged here as a genuine open question
  for the next package, not silently dropped from the brief.
- **The Group Photo capture prompt** (brief Part 11's "Your Event
  Highlights needs a group photo. Capture one now," before Round 1
  and/or before completion). Per the brief's own explicit "implement
  only if it can be done cleanly without expanding scope
  significantly, otherwise report the recommended insertion point" --
  not attempted this session, given everything else in this brief. My
  recommended insertion point for the next package: the trip's "Begin
  Round 1" action (`BeginRoundModal.tsx`) is the natural moment
  organisers are already gathered as a group, before anyone has
  dispersed to their own holes -- a skippable prompt there, checking
  `trips.group_photo_moment_id IS NULL` first, would need no new
  schema (the column already exists from V1.4) and would fit the
  existing "don't make this feel like extra admin" principle this
  whole feature has followed throughout.
- **Section 16's "generated slides use system-controlled timing rather
  than blindly applying photo duration"** -- not attempted. The
  existing player's timer is per-slide-kind already (photo duration
  vs. +2s for structural slides, vs. a video's own real duration for
  Bloopers), which is a reasonable approximation of "system-controlled
  timing," but no further differentiation (e.g. a longer dwell on a
  Champion slide specifically) was added, per the brief's own "do not
  introduce unnecessary timing complexity in this package."
